## 1. 문제점

### 1-1. 도착 판정 반경이 배보다 작음 (제일 큼)

```
선박 길이      14.18 m
도착 판정 반경   3.0 m   (vessel_gym.py: GOAL_REACHED)
```

배 길이의 0.21배짜리 원에 중심을 맞춰야 도착으로 침. 373m 항해해 와서.

실측 결과:

- 시간초과 배도 100% 가 목표 20m 이내까지 접근함. 최소접근 중앙값 11.0m (0.78척)
- 판정 반경만 바꿔 다시 세면 12m → 88.5%, 14.18m(1척) → 약 90%, 20m → 100%
- 현재 3m 기준 도착률 63%

궤적을 그려보니 시간초과 배는 목표 주변 반경 42m 원을 그리며 도는 극한 순환에 빠짐.
에피소드의 71%(2129결정)를 목표 80m 안에서 보냄. 그동안 가장 가까운 타선이 56.8m,
레이더에 아무도 없는 시간이 44.8%. 즉 교통 때문이 아니라 혼자 도는 것임.

도는 게 손해도 아님. 궤도 중 per-decision 보상이

```
시간 페널티 -0.07 + 전진보너스 0.1x0.92 - 연료 0.017 = +0.005   (x10 = +0.05)
```

전진 보너스가 시간 페널티를 덮음. 진행 보상은 telescoping 이라 한 바퀴 돌면 0,
각도 보상은 목표가 옆구리(90도)라 cos=0. 3000결정 돌면 +150 인데 도착 보상이 +150 임.

그림: `runs/traj_timeout.png`

### 1-2. 통신이 실행 중에는 일을 안 함

fc2 의 메시지 슬라이스 가중치를 다른 입력과 비교하면

| | 메시지 가중치 / 나머지 |
|---|---|
| actor | 0.12 ~ 0.26 |
| critic | 1.20 ~ 2.44 |

게이트도 actor 0.45~0.50, critic 0.58~0.69.

조타를 정하는 망은 메시지를 거의 안 읽고, 가치를 추정하는 망이 세게 읽음.
보상에 레이더 밖(56~420m) 충돌위험 항이 있어서 critic 이 그걸 예측하려면 메시지가 필요함.
actor 는 그럴 이유가 없음. 지금 타각은 36m 앞의 배가 정하고 그건 레이더에 보임.

즉 통신이 협조 채널이 아니라 critic 정보원(CTDE)으로 작동 중임.

뒷받침하는 관측:

- 런타임에 통신 차단해도 성능 동일 (3시드 페어: 켬 55.6/2.10/52.6, 끔 56.3/1.65/53.1)
- 레이더 사각지대에서도 메시지의 조타 영향 동일 (0.292 vs 0.310)
- 메시지 차원 2~12 가 무의미 (Fig4)
- 혼합 함대에서 통신 되는 배가 안 나음
- 메시지에 가장 강하게 실린 게 조우상황(R2=0.48)인데 이건 받는 쪽이 기하로 계산 가능한 공개 정보.
  레이더로 못 보는 목적지 방위는 R2 0.24/0.15 로 약함 (선형 프로브라 과소평가 가능)

그래도 효과 자체는 있음. 충돌 2.77% → 1.83%, 34% 감소, 3시드 전승.

## 2. 할 일

### 1순위. 도착 판정 반경 고치고 재학습

이게 나머지를 다 푸는 열쇠임. 시간초과가 걷히면 도착률 90%대가 되고,
남는 실패가 충돌 중심이 되어 통신·구조 효과가 종합 지표에 드러남.

`vessel_gym.py` 의 `GOAL_REACHED = 3.0` 을 배 길이 기준으로 올림.
근거는 선박 길이 14.18m, 근접 벌점 임계 19.6m(1.4척). 3m 는 자기 몸길이의 0.21배로 물리적으로 부자연스러움.
해사 실무에서도 도착은 접안 구역이지 점이 아님.

권장 14.18m (1척 길이). 보수적으로 가려면 10m.

주의. 재평가만 하면(기존 체크포인트에 반경만 바꿔 평가) 정책은 여전히 궤도를 돌고 첫 진입에서 끝날 뿐임.
제대로 하려면 재학습해야 궤도 자체가 안 생김.

### 2순위. 난수 메시지 대조군

충돌 감소가 메시지 내용 때문인지, 메시지 경로라는 추가 파라미터·gradient 경로가
정규화처럼 작용한 것인지 아직 안 갈림.

메시지 자리에 진짜 메시지 대신 난수를 넣고 학습시키는 팔을 3시드 돌릴 것.
그래도 OFF 보다 좋으면 이득은 정보가 아니라 구조에서 온 것이고 통신이라 부를 수 없음.

심사자가 먼저 물어볼 대조군이므로 우리가 갖고 있는 게 나음.

### 3순위. Fig6 처리

3시드 유지는 안 됨. 이미 5시드를 돌려놓고 3개만 쓰는 것이라 위험함.

### 4순위. x축 15M 근거 세우기

원칙적인 이유를 대거나 16M 까지 그릴 것. 지금은 근거가 없음.
16M 까지 그리면 Fig1 이 뒤집히므로 결론이 절단에 의존한다는 사실 자체를 정직하게 다뤄야 함.

### 5순위. 종료 파도 처리

파도 창(종료수가 그 실행 중앙값의 2배 초과)을 빼고 곡선을 그리는 것이 정석임.

## 3. 다른 컴퓨터에서 돌릴 때

```
git clone https://github.com/DragonTrainerTristana/DT_Vessel.git
cd DT_Vessel
git checkout Shared_MoE
```

구조는 브랜치 기본값에 의존하지 말고 env 를 명시할 것. 그러면 어느 브랜치에서든 같은 구조가 나옴.
브랜치별 기본값은 `RUNS.md` 2절.

학습:

```
VESSEL_MSG_DIM=6 VESSEL_USE_MOE=1 VESSEL_MOE_SHARED=1 VESSEL_MOE_WIDTH=1.0 \
VESSEL_USE_COMM=1 VESSEL_RADAR_RANGE=56 VESSEL_THREAT_COEF=0.5 \
VESSEL_SIM_COLREGS_COEF=0.45 VESSEL_POS_GROUND=1 VESSEL_USE_ATTENTION=0 \
python vessel_gym_train.py --arm ON --comm_on_at 9000000 --max_partners 4 --seed 42 \
    --envs 128 --vessels 16 --rollout 32 --steps 16000000 --ring 0.7 \
    --save <프로젝트폴더>/checkpoints/<이름>.pt --csv <...>.csv
```

임시 폴더에 저장하지 말 것. Storage Sense 가 지움.

평가:

```
<위와 같은 env> \
python eval_ckpt.py --ckpt <ckpt> --arm ON --max_partners 4 \
    --envs 96 --burnin 1500 --eval_decisions 3500
```

그림:

```

python regenerate_all.py     # 곡선. VESSEL_FIG_XMAX 가 여기서 주입됨
```

한 시드 학습이 GPU 하나로 약 1시간(통신 9M 팔), 통신 0M 팔은 3~5시간.
두 레인 병렬로 돌리면 각각 1.75배 느려지지만 전체 처리량은 이득임.
